- #7 **Subagent turns are deduplicated in `agents` but not in `list` / `show` / `inputs`.** All three over-count subagent spend today; the agents view is the only one that does not.
  - `build_subagent_turns` and `build_subagent_meta` (`src/loading.rs:568`, `:595`) both skip the `(message_id, request_id)` dedup pass that `load_sessions` runs over parent transcripts. Their shared doc comment states the omission and justifies it as "subagent transcripts are non-resumable single-file, so the key set never fires across them" — that reasoning is about *cross-file* identity and does not cover repeats *within* one transcript, which is what actually inflates the totals.
  - `load_agents` deduplicates with a `seen` set scoped to each single transcript (`build_dispatch`), which is what makes the agents view's figures trustworthy. The fix for the other three is likely the same scope, not the per-project one `load_sessions` uses for resumed conversations.
  - The design behind the agents view measured **167% aggregate inflation** without this pass. Treat that as the order of magnitude at stake, not a precise current figure.
  - Deliberately excluded from the agents-view plan (its "What We're NOT Doing" named it as its own investigation) so the `list` / `show` `insta` baselines would not move. Fixing it *will* move those baselines — that is the signal it worked, not a regression to avoid.
  - Design with the rationale: `$THOUGHTS_DIR/designs/2026-09-07-cclens-agents-view-subagent-cost-attribution.md`.
- #1 Inputs TUI per-file session breakdown drill-down. Pressing Enter on an attribution row shows which sessions loaded the file and at which tier, similar to the list→show pattern. Requires building a per-file-per-session evidence data pipeline and adding a View enum to the inputs TUI.
- #2 TUI refresh: explore fs-notification-based change detection. The current 3s polling interval works but runs `discover()` (full project tree walk + per-file stat) every tick. If this becomes a problem for power users with large project trees, prefer switching to OS-level file notifications (`notify` crate: kqueue on macOS, inotify on Linux) over tuning the poll interval. Incremental parsing (seek to byte offset, parse only new lines) would also reduce reload cost for active sessions.
- #3 TUI in-flight ledger: a panic in `spawn_load`'s `map` closure leaks its slot forever. `spawn_load` (`src/tui.rs`) wraps `load` in `catch_unwind`, but calls `map(outcome, ...)` outside it, so a panic there aborts the `spawn_blocking` task before `tx.send` — no result arrives, `handle_load_result` never releases the reservation, and every later dispatch for that slot is suppressed. The scope then stops refreshing, silently. Pre-existing (the `refresh_in_flight` boolean had the same failure mode), but `App.in_flight`'s doc comment now asserts a strict reserve/release symmetry that this one path breaks. Likely shape: move the `map` call inside `catch_unwind`, or send a synthesized failure result from a guard object dropped on unwind.
- #4 TUI status footer: a `from_refresh_failure: false` status can persist indefinitely on an idle machine, masking the derived unpriced-rows hint. `handle_load_result`'s `NoChange` arm (`src/tui.rs`) deliberately clears only statuses stamped `from_refresh_failure: true` — a status from anywhere else (notably `apply_pricing`'s `Err` arm) is cleared only by a later _successful load_. With no new session activity, no successful load ever arrives, so a failed pricing refresh stays on the footer for the life of the session. Pre-existing, but `render_status_footer`'s precedence (a status takes the row outright) makes it observable: the masked content is the unpriced-rows hint, and a failed pricing refresh is exactly the situation in which that hint is most relevant. Likely shape: give the pricing-refresh status its own expiry, or let a successful _guarded_ refresh clear any user-triggered status once the condition that raised it no longer holds. Weigh against the reason the distinction exists — a user-triggered error must not vanish within one ~3s idle tick before anyone reads it.

Deferred deliberately during review rather than expanded ad hoc, since the right shape is probably a TUI section covering tabs, navigation, `p` pricing, `f` filter, and the active-filter indicator — not a paragraph bolted onto the filtering bullets. - #8 **`load_agents` pays for work it discards.** Two independent costs, both avoidable, neither yet measured.
  - **Inventory tokenization.** `discover_inventory` runs tiktoken over every context file, but `load_agents` reads only `path`, `kind`, and `scope` — nothing in `src/agents.rs` touches `ContextFile.tokens`. On a real `~/.claude` that is the whole `inputs` tokenization pass, spent to produce a field the view never reads. Likely shape: a paths-only walk mode on `inventory`, with `discover_inventory` keeping today's behavior for `load_inputs`.
  - **Parent transcript parsing.** Every parent session carrying subagents is fully deserialized by `parse_jsonl` purely to `find_map` its first `cwd` (`src/loading.rs`, in `load_agents`). Likely shape: a scan that stops at the first line carrying a `cwd`, rather than parsing to completion.
  - Together these make the agents view cost roughly `load_sessions` plus the inputs tokenization pass. Raised during the Phase 2 review of the agents-view plan and deferred deliberately: the view did not exist yet, so the cost could not be measured, and reshaping `inventory`'s public surface mid-plan for an unmeasured cost was the wrong trade.
  - **Measure before optimizing.** Time `cclens agents --format plain` against the real `~/.claude/projects` first; if it is already fast enough at that scale, close this rather than acting on it.
