- #1 Inputs TUI per-file session breakdown drill-down. Pressing Enter on an attribution row shows which sessions loaded the file and at which tier, similar to the list→show pattern. Requires building a per-file-per-session evidence data pipeline and adding a View enum to the inputs TUI.
- #2 TUI refresh: explore fs-notification-based change detection. The current 3s polling interval works but runs `discover()` (full project tree walk + per-file stat) every tick. If this becomes a problem for power users with large project trees, prefer switching to OS-level file notifications (`notify` crate: kqueue on macOS, inotify on Linux) over tuning the poll interval. Incremental parsing (seek to byte offset, parse only new lines) would also reduce reload cost for active sessions.
- #3 TUI in-flight ledger: a panic in `spawn_load`'s `map` closure leaks its slot forever. `spawn_load` (`src/tui.rs`) wraps `load` in `catch_unwind`, but calls `map(outcome, ...)` outside it, so a panic there aborts the `spawn_blocking` task before `tx.send` — no result arrives, `handle_load_result` never releases the reservation, and every later dispatch for that slot is suppressed. The scope then stops refreshing, silently. Pre-existing (the `refresh_in_flight` boolean had the same failure mode), but `App.in_flight`'s doc comment now asserts a strict reserve/release symmetry that this one path breaks. Likely shape: move the `map` call inside `catch_unwind`, or send a synthesized failure result from a guard object dropped on unwind.
- #4 TUI status footer: a `from_refresh_failure: false` status can persist indefinitely on an idle machine, masking the derived unpriced-rows hint. `handle_load_result`'s `NoChange` arm (`src/tui.rs`) deliberately clears only statuses stamped `from_refresh_failure: true` — a status from anywhere else (notably `apply_pricing`'s `Err` arm) is cleared only by a later _successful load_. With no new session activity, no successful load ever arrives, so a failed pricing refresh stays on the footer for the life of the session. Pre-existing, but `render_status_footer`'s precedence (a status takes the row outright) makes it observable: the masked content is the unpriced-rows hint, and a failed pricing refresh is exactly the situation in which that hint is most relevant. Likely shape: give the pricing-refresh status its own expiry, or let a successful _guarded_ refresh clear any user-triggered status once the condition that raised it no longer holds. Weigh against the reason the distinction exists — a user-triggered error must not vanish within one ~3s idle tick before anyone reads it.

- #8 **`load_agents` pays for work it discards.** One avoidable cost, not yet measured.
  - **Inventory tokenization.** `discover_inventory` runs tiktoken over every context file, but `load_agents` reads only `path`, `kind`, and `scope` — nothing in `src/agents.rs` touches `ContextFile.tokens`. On a real `~/.claude` that is the whole `inputs` tokenization pass, spent to produce a field the view never reads. Likely shape: a paths-only walk mode on `inventory`, with `discover_inventory` keeping today's behavior for `load_inputs`.
  - The loading walk (`ProjectWalk` in `src/loading.rs`) parses every parent transcript in full, because continuation lineage and project-wide dedup need it, so parent parsing is no longer a cost this loader can skip. Measure against the loader as it now stands.
  - The same walk holds every parsed parent of a project in memory at once, and `show` parses every parent in its target's project rather than stopping at the target, so `show` and `inputs` pay the parse and peak-memory cost too. Measure `cclens show <id>` and `cclens inputs` on a large project alongside `agents`. The largest local project holds about 110 MB of parent JSONL. Likely shape if it matters: ordering needs only each parent's `continued-in` targets, cwd, and short name, so the first phase could keep just those and `next` re-parse the parent — peak memory bounded by one transcript, at the cost of reading every parent twice.
  - Together these make the agents view cost roughly `load_sessions` plus the inputs tokenization pass. Raised during the Phase 2 review of the agents-view plan and deferred deliberately: the view did not exist yet, so the cost could not be measured, and reshaping `inventory`'s public surface mid-plan for an unmeasured cost was the wrong trade.
  - **Measure before optimizing.** Time `cclens agents --format plain` against the real `~/.claude/projects` first; if it is already fast enough at that scale, close this rather than acting on it.
- #9 **`Exchange` can hold an `origin` that disagrees with its turns.** `Exchange { user: Option<&Turn>, assistants, origin }` in `src/aggregation.rs` stores `origin` beside the turns it derives from, and the public fields let a hand-built value pair `user: Some(&u)` with an `origin` other than `u.origin`, sending it down the wrong `prepare_exchanges` branch. "A user-less exchange has at least one assistant" is likewise a doc comment, not a type: `Exchange { user: None, assistants: vec![] }` renders `0` tokens where an orphan renders `—`. `group_into_exchanges` keeps both invariants, so only hand-built values (tests, future callers) can break them.
  - Likely shape: derive `origin()` from `user.or(assistants.first())`, or lead with an enum (`User(&Turn)` / `Continuation(first assistant)`) so neither bad state can be constructed.
- #10 **`agents` cost differs from `list` for the same transcript.** `dispatch_from_turns` (`src/agents.rs`) prices a transcript's summed usage once at its majority model, so the 200k price tier applies to the sum rather than per message, and `--compare-model` reprices the summed rows the same way. Token figures agree across views; cost does not.
- #11 **Credit a cold-resumed continuation's replayed skill loads in `inputs`.** Project-wide dedup counts a skill load a `continued-in` continuation replays once, under the original session. When the continuation resumes after the prompt cache has expired, its first request writes the replayed history (skill text included) to the cache again. That spend lands in the continuation's observed cache-creation tokens, but `inputs` credits the skill no load for it, so attribution and coverage for those sessions read low. A warm resume reads the cache instead, and crediting once is correct.
  - Pinned by `inputs_counts_a_replayed_skill_load_once` (`tests/continuation.rs`); `dedup_turns` in `src/aggregation.rs` drops the replayed load before `session_meta_from_turns` sees it.
  - Likely shape: decide per continuation whether its first assistant turn re-created the cache for the replayed prefix (cache-creation tokens on that turn vs. a cache read), and if so credit the replayed loads to the continuation as well.
- #12 **`show`'s `continuation` row claims a lineage it never checks.** Any assistant turns before the first substantive user turn open a user-less `continuation` exchange (`group_into_exchanges` in `src/aggregation.rs`, the `Role::Assistant` arm with no current exchange), not only a real continuation's.
  - Example: a fresh session whose first prompt is image-only has no display string, so `is_substantive_user_turn` is false and the reply renders as a `continuation` row.
  - The README's `show` section ("a continuation picking up mid tool loop") and the `Exchange` doc describe the row as a continuation, which the code does not verify.
  - Likely shape: untangle the label from the condition — treat an image-only prompt as substantive, or check `continued-in` lineage — rather than documenting the gap as intended.
- #13 **A `--fork-session` copy can take its original's opening prompt.** A fork copy has no `continued-in` record, so `ProjectWalk` orders it against the original by mtime (`lineage_order`'s fallback in `src/loading.rs`).
  - If the user keeps working in the original after forking, the original is the newer file, so the fork is fed first and claims the shared opening lines. The original's `list` title becomes its first post-fork prompt and its `show` opens with a `continuation` row.
  - Likely shape: find a lineage marker fork copies carry (sidecar field, first-line record, `forkedFrom`-style id) and feed it to `lineage_order` alongside `continued-in`.
- #14 **Replayed history double-counts across project directories.** `ProjectWalk`'s `SeenTurns` spans one project directory, so a continuation written under a different project (the session's cwd changed) re-counts everything it replayed.
  - Not observed locally; both local `continued-in` pairs stay within one project.
  - Likely shape: resolve `continued-in` targets across projects, or hoist the seen-set above the per-project loop with a lineage order spanning projects.
- #15 **An assistant message split across two files would undercount output.** `parse_jsonl` merges a message's lines within one file, then `dedup_turns` keeps the first file's merged turn by message key and drops the later file's whole turn — including its later, higher `output_tokens`.
  - Unconfirmed whether Claude Code ever ends a transcript mid-message and replays the rest into a continuation. Locally, the first line of a split message carries the lower output count in 5,927 of 5,935 messages whose lines differ, so the loss would be real if the shape exists.
  - Likely shape: on a cross-file message-key hit, merge the later turn's blocks and usage into the earlier one instead of dropping it — which needs dedup to reach back into an already-yielded session.
