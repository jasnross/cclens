- #1 Inputs TUI per-file session breakdown drill-down. Pressing Enter on an attribution row shows which sessions loaded the file and at which tier, similar to the list→show pattern. Requires building a per-file-per-session evidence data pipeline and adding a View enum to the inputs TUI.
- #2 TUI refresh: explore fs-notification-based change detection. The current 3s polling interval works but runs `discover()` (full project tree walk + per-file stat) every tick. If this becomes a problem for power users with large project trees, prefer switching to OS-level file notifications (`notify` crate: kqueue on macOS, inotify on Linux) over tuning the poll interval. Incremental parsing (seek to byte offset, parse only new lines) would also reduce reload cost for active sessions.
- #3 TUI in-flight ledger: a panic in `spawn_load`'s `map` closure leaks its slot forever. `spawn_load` (`src/tui.rs`) wraps `load` in `catch_unwind`, but calls `map(outcome, ...)` outside it, so a panic there aborts the `spawn_blocking` task before `tx.send` — no result arrives, `handle_load_result` never releases the reservation, and every later dispatch for that slot is suppressed. The scope then stops refreshing, silently. Pre-existing (the `refresh_in_flight` boolean had the same failure mode), but `App.in_flight`'s doc comment now asserts a strict reserve/release symmetry that this one path breaks. Likely shape: move the `map` call inside `catch_unwind`, or send a synthesized failure result from a guard object dropped on unwind.
- #4 TUI status footer: a `from_refresh_failure: false` status can persist indefinitely on an idle machine, masking the derived unpriced-rows hint. `handle_load_result`'s `NoChange` arm (`src/tui.rs`) deliberately clears only statuses stamped `from_refresh_failure: true` — a status from anywhere else (notably `apply_pricing`'s `Err` arm) is cleared only by a later *successful load*. With no new session activity, no successful load ever arrives, so a failed pricing refresh stays on the footer for the life of the session. Pre-existing, but `render_status_footer`'s precedence (a status takes the row outright) makes it observable: the masked content is the unpriced-rows hint, and a failed pricing refresh is exactly the situation in which that hint is most relevant. Likely shape: give the pricing-refresh status its own expiry, or let a successful *guarded* refresh clear any user-triggered status once the condition that raised it no longer holds. Weigh against the reason the distinction exists — a user-triggered error must not vanish within one ~3s idle tick before anyone reads it.
- #5 README: document the TUI. The README describes the CLI surface only — `cclens list` / `show` / `inputs` flags and output — with no mention that a TUI exists, let alone its keys. Deferred deliberately during review rather than expanded ad hoc, since the right shape is probably a TUI section covering tabs, navigation, `p` pricing, `f` filter, and the active-filter indicator — not a paragraph bolted onto the filtering bullets. Worth doing once the TUI's key bindings settle.
